# 双端协同开发最佳实践 v1.0

> 版本: v1.0 | 创建: 2026-08-07 | 适用: AI数智名片（本地电脑 + 手机/远程分身双端开发）
> 原则: 单仓库、双入口、零冲突、PRD 驱动、三级确认

---

## 一、双端定位（谁在哪端开发）

| 开发端 | 适合做什么 | 不适合做什么 |
|:-------|:-----------|:-------------|
| **本地电脑**（Windows Hermes + 微信开发者工具 + IDE） | 大功能开发、UI/交互密集改动、需要本地调试的（小程序预览/断点）、批量文件操作 | 服务器侧适配、运行时配置（nginx/服务脚本）、需要在生产环境验证的改动 |
| **手机/远程分身**（飞书指挥服务器白泽） | 服务器侧修复、cron/脚本运维、知识库反哺、紧急修复、巡检监控、**上线操作（三级确认）** | 大批量 UI 开发、需要本地工具链验证的改动 |

**一句话**：本地做"重活"（功能/UI），远程做"轻活"（修复/运维/上线）。两端不同时改同一批文件。

## 二、防冲突铁律（零干扰的根基）

### 铁律 1: 单一事实源 = GitHub origin
- 两端永远以 `git pull` 后的代码为开发基线，**不以本地工作区为准**
- 开发前必 `git checkout develop && git pull`
- 不推送 = 没做完（本地关机/未 push 的改动，另一端看不到 = 当作不存在）

### 铁律 2: 分支即隔离墙（永远不要在 master/develop 上直接改）
```
master ← 生产（只进不出，三级确认第3步才动）
  ↑
releaseV1.0 ← 发布候选（三级确认第2步）
  ↑
develop ← 日常开发集成分支（feature 合并目标）
  ├── feature/xxx  ← 所有开发从这里出
```

### 铁律 3: 同一时刻只有一个 feature 分支被"持有"
- 两端开工前先互相确认：**"我现在要改 feature/xxx，你有在动吗？"**
- 分支命名带端标识，一眼可辨：
  - 本地开发: `feature/local-xxx`（如 `feature/local-card-editor`）
  - 远程开发: `feature/remote-xxx`（如 `feature/remote-fix-cron`）
- 冲突的物理防线：两端都 pull 最新 → 若有人已 push 相同区域，merge/push 时必然暴露，**冲突即信号，停下沟通，不要强推**

### 铁律 4: 同内容双 hash 分叉防再犯
- **症状**：`git rev-list --left-right --count origin/master...master` 出现大数字分叉，但提交主题几乎一样
- **成因**：同一批改动在两端被各自 commit 一次（内容同、hash 不同）
- **预防**：每次 commit 前先 `git pull --rebase`；开发完立刻 push；绝不攒着一堆 commit 最后一次性 push
- **检测**：`git log --oneline --cherry-pick --right-only origin/master...master` 看真实差异

## 三、PRD 驱动开发流程（逐步推进）

### Step 0: 从 PRD 选任务
- 打开 `docs/PRD.md`，按 P0 → P1 → P2 优先级选一条
- 确认该功能状态标记（✅ 已完成 / ⚠️ 部分 / ❌ 未开始）
- **一次只做一条 PRD 条目**，做完验证完再选下一条（不并行开多条战线）

### Step 1: 建分支（带 PRD 编号）
```bash
cd /var/www/ai-digital-card   # 服务器端
git checkout develop && git pull
git checkout -b feature/remote-PRD-2.1.2-brochure
# 本地端对应: feature/local-PRD-2.1.2-brochure
```

### Step 2: 开发 + 小步提交
- 按 `feat:/fix:/refactor:/style:/docs:` 规范分组提交
- 每个逻辑单元一个 commit，**不攒大 commit**
- 提交前 `git diff --cached --stat` 确认无凭证/无无关文件

### Step 3: 测试门禁（合规门槛）
```bash
# 后端 API 契约门禁（必须全过）
cd backend && venv/bin/pytest tests/test_api_standards.py
# 后端 graphql
venv/bin/pytest tests/test_graphql.py
```
- 失败先基线验证（`git stash` → 重跑 → `git stash pop`），不归因自己也不顺手扩大范围

### Step 4: 推送 feature 分支
```bash
git push -u origin feature/xxx
```

### Step 5: RELEASE 文档（达到 release 门槛时）
- 用 `docs/RELEASE_v<版本>.md` 模板：变更清单 / 验证记录 / 已知限制 / 回滚方法

### Step 6: 三级确认上线（两端都必须走，不能绕过）
```
Step 1: 用户说「确认」→ feature 合并 develop
Step 2: 用户再确认 → develop 合并 releaseV1.0
Step 3: 用户说「上线」→ releaseV1.0 合并 master + 打 tag + 部署
```
- **只有合并到 master 才算上线**
- 手机端远程分身可以执行整个流程，但**每步都等海容亲口确认**（watchdog 只通知不合并）

## 四、两端协作的每日节奏（推荐）

| 时间 | 动作 | 端 |
|:-----|:-----|:---|
| 开机 | 本地 `git pull` + skills 双向同步 + 知识库同步 | 本地 |
| 白天 | 大功能开发（本地） / 远程巡检+修复（手机） | 双端 |
| 任意时刻 | 改动完成 → 推 feature 分支 → 飞书告知另一端 | 双端 |
| 每晚 | 飞书汇总当日 feature 分支 + 待确认项清单 | 远程分身 |
| 有「确认」/「上线」 | 按三级确认执行 | 手机远程 |

## 六、常见问题

**Q: 两端都想改同一块代码怎么办？**
A: 不并行。先到先得，后者等前者 push 完 pull 后再开工；或分工：一个改后端、一个改前端。

**Q: 手机端远程改完，本地怎么拿？**
A: `git pull origin develop`（feature 合并后）或 `git fetch && git checkout feature/xxx`（未合并前）。

**Q: 本地改了没推送就关机？**
A: 远程分身会把它当不存在。开机第一件事就是 `git pull` + 补 push，遵守"不推送=没做完"。

**Q: 分叉已经发生了怎么办？**
A: 见第二节铁律 4 检测法 → 用 `--cherry-pick` 找出真实差异 → 备份分支 → rebase → push（参考 2026-08-07 方案A实战，已反哺盖娅 id 7805）。
